# Frontend Fundamentals 모의고사

## Getting started

```sh
yarn dev
```

## 설계 시 고려사항

### 1. 에러 처리

#### 런타임 데이터 안전성 확보

서버에서 오는 응답이 항상 기대한 형태라는 것을 보장할 수 없기 때문에, Zod를 통해 런타임 검증을 수행해 데이터 신뢰성을 보장하려고 했습니다.
잘못된 데이터가 전파되는 것을 사전에 차단하는 것이 목적입니다.

#### 에러 종류 분리

- HTTP 에러
  - 네트워크 실패, 서버 오류 등 통신 계층의 문제
  - 메시지: “적금 상품 조회 실패”
- 검증 에러 (ZodError)
  - 응답 구조가 스키마와 불일치할 때 발생
  - 메시지: “적금 상품 데이터 검증 실패”

### 2. 비동기 데이터 처리

#### Suspense 기반 데이터 흐름 처리

Suspense를 사용해 로딩/에러/성공 흐름을 분리하고, 컴포넌트에서는 성공 시점의 데이터만 다루도록 구성했습니다.

- 로딩 중: Promise throw -> Suspense가 fallback UI 표시
- 에러 발생: Error throw -> ErrorBoundary가 fallback UI 표시
- 성공: 데이터 반환 -> 컴포넌트 정상 렌더링

### 3. 로컬 상태 관리

#### 로컬 상태 선택 이유

savingsValues(목표 금액, 월 납입액, 저축 기간)와 selectedProductId는 SavingsCalculatorPage 내부에서만 사용되는 로컬 상태이며 다른 페이지나 기능에서 필요하지 않습니다.
전역 상태를 도입할 경우 오히려 보일러플레이트가 증가하고 현재 과제 규모에서는 오버엔지니어링이라 판단했습니다.
따라서 props로 전달하는 것이 적절하다 생각했습니다.

#### 상태 위치

- 상태가 필요한 최소 공통 부모에 상태를 선언
- 상태 변경 핸들러도 같은 위치에서 정의 (상태 변경 로직과 상태의 관계 파악 쉬움)
- 자식 컴포넌트에서는 함수의 동작을 모르고 사용만 하도록 설계

### 4. 컴포넌트 책임 분리

- 각 컴포넌트가 하나의 책임만 수행하도록 설계
  - Inputs: 사용자 입력 처리 + 상위에 알림
  - ProductList: 상품 목록 표시 + 선택 처리
  - CalculationResult: 계산 결과 출력
  - Contents: 탭 관리 및 탭에 따른 콘텐츠 표시
  - RecommendedProductList: 상품 상위 2개 추출 로직 포함

## 궁금한 점

### 1. Fallback UI 처리

현재 SuspenseFallback / ErrorFallback이 단순한 텍스트 형태로 되어 있습니다.
실제 서비스에서는 어떤 기준(기능, 중요도, ...)으로 다음 요소들을 어느 수준까지 적용하는 것이 적절할지 궁금합니다.

**로딩 (Suspense fallback)**

- 로딩 스피너
- Skeleton UI

**에러 (ErrorBoundary fallback)**

- 에러 메시지
- 재시도 버튼
- 홈으로 이동 같은 대체 경로 제공

### 2. 사용자 입력값 로컬 상태 유지 방식

현재 사용자 입력 데이터가 컴포넌트 로컬 상태에만 저장되어 있어, 페이지 리프레시 시 입력 데이터가 모두 초기화되는 구조입니다.
아래 옵션의 트레이드오프와 적절한 사용 시기에 대해 의견을 듣고 싶습니다.

#### 저장 방식 옵션

1. 유지하지 않는다 (현재 방식)
2. localStorage 등 브라우저 저장소에 저장
3. URL 파라미터로 저장
4. 백엔드 DB에 저장

### 3. Query Key 설계

현재 Query Key를 단순하게 문자열 배열로 구성했습니다.

```typescript
queryKey: ['savingsProductList'];
```

Query Key를 어떻게 구조화하고 관리하는 것이 좋을지 궁금합니다.

**고려 사항:**

- Query Key 네이밍 컨벤션
- Query Key 중복 방지 및 일관성 유지 방식
- 필터링/페이지네이션 추가 시 Query Key 관리 방식

### 4. 컴포넌트 추상화 수준

- ProductList와 RecommendedProductList의 구조가 비슷한데, 추상화 할 가치가 있을지 궁금합니다.
- Product가 ListRow 형태로 반복되는데, 추상화 할 가치가 있을지 궁금합니다.
